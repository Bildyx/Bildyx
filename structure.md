# Bildyx

## Overview
Job/career reference platform (industries, countries, cities, jobs, organizations, skills, etc.) with a marketing website and a backend API.

## Tech Stack
- **Language**: TypeScript (backend), PHP/HTML (website)
- **Framework**: Express (API), Prisma (schema/migrations only)
- **Key dependencies**: Kysely (actual query builder, using `apps/api/src/db/types.ts` generated by kysely-codegen), Zod (API validation), pg
- **Build / runtime**: npm workspaces (root `package.json`), tsx

## Project Structure
```
apps/
├── api/                  # Backend API (Express + Kysely + Prisma schema)
│   ├── prisma/
│   │   ├── schema.prisma # Source of truth for DB schema (Prisma migrations)
│   │   ├── seeds/         # Legacy createMany/skipDuplicates seeders (still used by `npm run seed`, unchanged)
│   │   └── import/        # Incremental CSV -> DB import engine (hash-based diff), see Recent Changes
│   ├── src/
│   │   ├── db/types.ts   # Kysely types generated from live DB (kysely-codegen) — can drift from schema.prisma if migrations aren't regenerated
│   │   ├── models/        # Zod schemas per resource, field names match snake_case DB columns
│   │   └── routes/        # Express routes per resource
│   ├── scripts/
│   │   ├── generate_excel_templates.py  # Generates .xlsx import templates from schema.prisma; also locks them down (see below)
│   │   ├── excel_to_csv.py              # Converts apps/api/data/excel_templates/*.xlsx into apps/api/data/*.csv (skips fully blank rows)
│   │   └── import.ts                    # CLI for apps/api/prisma/import/ — `npm run import -- --model X --file Y` or `--all`
│   └── data/
│       ├── *.csv                 # CSVs generated from data/excel_templates via excel_to_csv.py
│       └── excel_templates/      # Generated .xlsx templates (one per reference model) — also doubles as the filled-in working data file (excel_to_csv.py reads from here, not a separate data/excel/)
└── website/               # Marketing site (PHP/HTML/CSS/JS)
Files/                      # Legacy hand-curated business data templates (csv/excel), unrelated to DB schema column names
```

## Architecture Notes
- The API layer uses **Kysely**, not Prisma Client, for queries. Prisma is used only for schema/migrations. Field names used in code (`models/*.ts`, `db/types.ts`) are DB column names (snake_case via `@map`/`@@map`), not the Prisma camelCase model field names.
- `Country.officialLanguages`, `Organization.numberOfEmployees`, and `Organization.numberOfSubsidiaries` intentionally have no `@map` in `schema.prisma` — confirmed via the applied migration SQL (`apps/api/prisma/migrations/20260708013135_init/migration.sql`) that the real DB columns are camelCase (quoted), matching `schema.prisma` and `db/types.ts` as-is. `organizations.csv`'s header uses the same camelCase for these two columns; the seed script reads them accordingly. The snake_case headers for these fields in `apps/api/data/*_rows.csv` are from a manually reformatted export, not the real column names — don't use those CSVs as a naming reference.
- Every FK field that logically points at an auto-generated UUID (`City.id`, `Organization.id`) must be resolved from the CSV's human-readable name via a DB lookup in the seed script (see `buildNameLookup` in `apps/api/prisma/seed-utils.ts`, used by `seeds_universities.ts`/`seeds_certifications.ts`/`seeds_subjects.ts`/`seeds_organizations.ts` (`city_id`)/`seeds_jobs.ts` (`industry_id`)) — the CSVs can't contain the real UUID since it doesn't exist until insertion. This does **not** apply to `Country`, since `Country.isoCode` is a stable natural key (2-letter code) known ahead of time; `City.countryId`/`University.countryId`/etc. reference it directly as `@db.Char(2)`, no lookup needed. `Organization.parentOrganizationId` is a self-reference (the parent row may not exist yet either) — `seeds_organizations.ts` pre-generates a `randomUUID()` per row up front (keyed by name) so every row's own id is known before insertion, inserts all rows with `parentOrganizationId: null` first, then does a second `update` pass to set it, avoiding FK-ordering failures if a child appears before its parent in the CSV.
- Implicit many-to-many relations (no FK column on either model at all, e.g. `Organization.countries` <-> `Country.organizations`) are exposed as a single free-text `;`-separated column on one side of each relation, via `M2M_COLUMNS` in `generate_excel_templates.py`: `organizations.xlsx` gets `countries` (ISO codes, matched directly like `city.country_id` — no lookup), `industries`, and `working_area_cities`; `cities.xlsx` gets `main_industries`; `subjects.xlsx` gets `industries`; `industries.xlsx` gets `related_industries` (the `Industry` self-relation — only `industries_A` is exposed, since it's symmetric and connecting one side satisfies the relation from both). Resolved at seed time by `seedManyToManyRelations()` (`apps/api/prisma/seeds/seeds_relations.ts`), which must run last in `seed.ts` since it references rows created by every other seeder.
- Models considered "reference data" (not tied to site auth/job-ad workflow): Industry, Country, City, Job, Organization, Skill, Certification, University, StudyFields, MilitaryCapabilities, Degree, Subject. These are the ones covered by `generate_excel_templates.py`. Excluded: JobAd, JobAdSkill, User, UserSession, UserProfile, UserCertifications, UserEducations, UserEducationFields, AuditLog.
